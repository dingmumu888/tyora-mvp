# TYORA Founder End-to-End Pilot

- Date: 2026-08-05
- Environment: Vercel Preview only
- Build: `codex/p0-community-visual-moderation` at `3c207a0`
- Preview: <https://tyora-bfev79i8f-dingmumu888s-projects.vercel.app/ask>
- Participant: TYORA founder alternating between a new product creator, a TYORA employee/Admin, a logged-out visitor, and—where community counters require it—a second ordinary member
- Method: Moderated remote think-aloud pilot with interleaved role/state-transition testing; desktop primary with mobile critical-path checks
- Status: Paused for the founder-approved P0 stabilization Batch A. Local implementation and automated verification pass; Preview-only database migration and a new Preview deployment are still pending. Do not retry the old blocked follow-up or owner deletion on the previous Preview build.
- Change rule: Record issues during the session; do not change product code until the full journey is complete

## Research questions

1. Can a first-time creator understand TYORA, register, complete onboarding, and publish an idea without technical help?
2. Does the public-to-admin-to-public loop make status, responsibility, privacy, and next actions clear?
3. Can the founder operate Community, private Custom, Source, Leads, Work Orders, content, and account administration without losing context?
4. Do mobile, multilingual, image, notification, privacy, and recovery paths remain usable across the whole journey?
5. Do the My TYORA Posts, Comments, Likes, I'd Buy, and Reviews counters match the actual records before and after every create, interaction, moderation, and removal action?

## Session rules

- Use Preview-only test data labelled `E2E 2026-08-05` wherever a title or note is available.
- Never place passwords, OTP codes, database details, certificates, private email addresses, or customer data in screenshots.
- Think aloud: say what you expect, what you are looking for, and what feels unclear before asking for help.
- For each completed stage, capture the success state and rate difficulty from 1 (very easy) to 5 (could not complete).
- If blocked, capture the screen before retrying. The moderator will record the issue and then give the smallest possible next hint.
- Do not permanently delete the E2E idea until reply, notification, return, revision, and republish have all been tested.
- Production is out of scope.
- Keep Creator, Admin, and Visitor sessions isolated in separate browser profiles/windows so cookies and permissions cannot mask role-boundary defects. Never expose Admin credentials, OTPs, or session data in screenshots.
- Execute each submission as one cross-role state machine: creator action, public visibility check where applicable, Admin queue/action check, then creator result check. The numbered stages are coverage groups, not a requirement to finish one role before switching.
- Treat every clickable button, link, tab, modal action, and browser return as a test transition. For each transition verify the destination, selected-language persistence, authorization boundary, draft/state persistence, error handling, and ability to return without data loss.
- Prefer concise text-only results for normal passes and repeated instances of an already evidenced issue. Capture a screenshot for the first occurrence of a new anomaly, a new page/state, an unclear result, or evidence that cannot be described unambiguously.
